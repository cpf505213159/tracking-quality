# 埋点数据质量监控与影响面回溯

六条质检规则 + 影响面估算，把「数据有问题」翻译成「哪个指标错了多少」。
数据用注入缺陷的生成器构造，所有检出率、误报率都对着真值算。

```bash
python scripts/run_all.py
```

---

## 一、要解决的问题

埋点出问题的时候，最常听到两句话是「今天数据好像不太对」和「这个数先别用了」。
两句话都没法执行。真正需要回答的是三件事：

1. **哪里坏了**——哪个端、哪个事件、从哪天开始
2. **坏了多少**——影响多少行、哪些指标被污染
3. **错了多少**——观测值和校正值差几个百分点

这个项目就是把这三点做成每日可跑的检查。

## 二、数据说明

公开数据集里没有「带缺陷标记的埋点日志」，而验证质检规则必须知道哪些行是坏的。
所以 `src/generate.py` 先造一份正常日志，再按剧本注入 6 类缺陷，并把剧本存成 `outputs/ground_truth.json`。
规则跑完以后，precision / recall 都是对着这份真值算的，不是自己说自己准。

| 项目 | 设定 |
|---|---|
| 规模 | 208,217 行事件 / 7,883 用户 / 59,999 会话 / 2024-06-01 起 31 天 |
| 漏斗 | view → detail → add_to_cart → order，会话深度按真实转化率衰减 |
| 平台 | iOS 34% / Android 41% / Web 25% |
| 注入缺陷 | 漏埋、重复上报、延迟、断点、顺序倒挂、字段异常、设备复用 |

### 字段说明（`outputs/events.csv`）

| 字段 | 说明 |
|---|---|
| `event_id` | 事件唯一 ID（重复上报时会出现两条相同 ID） |
| `user_id` / `device_id` / `session_id` | 用户 / 设备 / 会话 |
| `event` | `view` / `detail` / `add_to_cart` / `order` |
| `event_time` | 客户端上报时间 |
| `server_time` | 服务端接收时间（延迟 = 二者之差） |
| `platform` | `ios` / `android` / `web`，注入非法值后会出现 `Android`、`iOS `、`web3` |
| `price` | 仅 order 事件有值，注入后出现 -1 与 0 |
| `flag_*` | 注入标记，**只用于评估，规则里绝不允许读** |

## 三、六条规则

| 规则 | 检查什么 | 判定方式 | 阈值 |
|---|---|---|---|
| R1 完整性 | 加购埋点整段缺失 | 各端「加购/商详」比值跌破基线 40% | 基线取 90 分位 |
| R2 唯一性 | SDK 重试导致重复上报 | `event_id` 重复率 | 1% |
| R3 及时性 | 上报延迟、整点断流 | 整点 p95 延迟、整点事件量为 0 | p95 > 600s |
| R4 一致性 | 漏斗顺序倒挂 | 会话内 order 时间早于 detail | 0.5% |
| R5 有效性 | 枚举越界、金额非正 | platform 不在白名单、order 金额 ≤ 0 | 0.5% |
| R6 设备一致性 | 一号多用户 | 一个 device_id 关联多个 user_id | 受影响会话 1% |

### R1 的基线为什么用 90 分位

第一版用「中位数 + MAD」的稳健 z 值，结果**漏报了整段缺失**：
30 天里有 20 天比值是 0，中位数被拉到 0、MAD 也变成 0，z 值恒为 0。
这是异常检测里很典型的陷阱——**当异常持续得足够久，它就成了「正常」**。
改用 90 分位代表健康水平，再配「跌幅 ≥ 40%」的业务阈值，才稳定。

## 四、结果

### 4.1 六条规则全部命中

```
❌ R1 完整性    android 端自 2024-06-11 起加购/商详比从 0.359 跌到 0.000（跌幅 100%），20 个平台日触发
❌ R2 唯一性    9,915 行 event_id 重复，去重后 198,302 行（重复率 4.76%）
❌ R3 及时性    4 个整点 p95 延迟超 600s（最高 10800s，峰值 06-18 20:00）；1 个整点无任何日志
❌ R4 一致性    150 个会话下单时间早于商详（占有效会话 3.0%）
❌ R5 有效性    platform 非法 4,160 行；订单金额非正 52 行；device_id 缺失 7.8%
❌ R6 设备一致性 580 个设备号关联多个用户，波及 4,634 个会话（7.7%）
```

### 4.2 检出质量（对着注入真值）

| 缺陷 | 判定粒度 | 注入 | 检出 | Precision | Recall |
|---|---|---:|---:|---:|---:|
| D2 重复上报 | event_id | 9,915 | 9,915 | 1.000 | 1.000 |
| D4 顺序倒挂 | session_id | 150 | 150 | 1.000 | 1.000 |
| D5 字段异常 | row | 4,212 | 4,212 | 1.000 | 1.000 |
| D6 设备复用 | device_id | 580 | 580 | 1.000 | 1.000 |

**为什么按不同粒度评估**：重复上报的两条记录 `event_id` 相同，谁才是副本永远无法判断，
所以只能在 event_id 维度判定——行级 precision/recall 没有意义。
顺序倒挂天生是会话级现象，设备复用天生是设备级现象。**缺陷的可检测粒度不同，评估口径就该不同。**

### 4.3 影响面：观测值 vs 校正值

| 指标 | 观测值 | 校正值 | 偏差 | 方向 |
|---|---:|---:|---:|---|
| 全站加购率 | 24.35% | 34.24% | **-9.88 pp** | 严重低估 |
| GMV | 615,076 | 620,248 | -0.8% | 轻微低估 |
| 事件量 PV | 208,217 | 198,302 | +5.0% | 高估 |

![指标偏差](figures/metric_bias.png)

**加购率被低估 9.88 个百分点（相对 40.6%）**，这是本项目最有业务价值的数字：
如果按这个观测值做决策，会得出「加购环节体验恶化」的错误结论，然后去优化一个根本没坏的地方。

校正方法：用 Android 端缺陷发生前 10 天的自身比值（0.350）外推 6/11 之后的商详量，
补回 3,435 个缺失的加购会话。这是外推，不是测量，报告里必须标明。

## 七、局限

1. **生成器不是真实日志**。真实埋点还会有人为改数、跨端 ID 不一致、SDK 本地缓存丢包等问题，这里只覆盖了 6 类最常见缺陷。
2. **影响面是估算**，不是测量。加购率校正依赖「缺陷前后转化率稳定」这个假设，如果同期还有活动，估计会有偏差。
3. **R3 只报整点粒度**。更细的分钟级断流会漏掉，但日级看板不需要那么细。
4. **没有做根因定位**。规则能定位到「哪个端哪个事件」，但不知道是发版漏传、参数改名还是网关丢包——那需要接发布系统和网关日志。

## 真实公开数据集

本仓库在 `data/real/` 附带**真实公开数据集**（来源、许可与字段说明见 `data/real/SOURCES.md`）。
运行 `python src/real_data_analysis.py` 可基于真实数据复现统计概览，输出到 `outputs/real_metrics.json` 与 `reports/real-data-notes.md`。

> 说明：`data/`、`outputs/metrics.json` 中的主结果是脱敏/仿真案例，用于稳定演示方法论；`data/real/` 使用公开真实数据集验证同一套方法在真实数据上可运行。
